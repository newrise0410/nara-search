# NARA SEARCH — 확장 로드맵 (2026-08-31)

## Context

001~008 런으로 초기 목표는 완료·배포됐다: 모노레포 + 수집 파이프라인(낙찰 8/25~27 35만 투찰행, 공고 8월 3.2만 건 중 첨부 89%, 계약 1주), 리디자인(방향 A), Google 로그인(이메일만 저장), 나라장터 실시간 공고 조회, 계정별 데이터 동기화, 알림 4채널 + 규칙 평가기, 일일 수집·15분 알림(GitHub Actions). DB 217MB.

이번 플랜은 그 다음 확장이다. 사용자 결정:
- **우선순위: ① 협업(팀 워크스페이스) → ② 안정화·운영.** 데이터·분석은 그 뒤.
- **백필 범위: 낙찰 3개월 + 공고·계약 1년** — 단, 아래 무료 티어 제약으로 "낙찰은 헤더+요약 3개월, 공고·계약 상세는 최근 창 보존 + 과거는 나라장터 실시간 검색"으로 조정.
- **유료 결제 없음(Supabase Pro 포함).** 무료 500MB 안에서 운영한다. 결제·플랜 업그레이드는 추후 결정.

설계 에이전트(Opus)가 코드 조사로 확인한 사실이 반영돼 있다: `/api/me/*`는 `server/me.ts` 헬퍼 4개가 단일 통과 지점이라 org 전환 시 라우트 15개가 무변경이고, 백로그 19건(B1~B19)이 REVIEW들에서 수집·재확인됐으며, 낙찰 백필은 파티션 자동 생성이 이미 동작한다.

## 무료 티어 데이터 예산 (실측: 투찰행 24MB/일 · 공고 62MB/월 · 계약 37MB/주 · 현재 217MB/500MB)

전량 보존은 증분만으로도 2주 내 한도 초과. 따라서 **"상세는 최근 창, 요약·헤더는 영구"**:

| 데이터 | 보존 정책 | 예산 |
|---|---|---|
| 낙찰 헤더(awards) + **투찰 요약**(jsonb: n·순위 상위 3·중앙 투찰율) | 영구 (~5MB/월) | 통계·추천 구간의 기반 |
| 투찰 상세행(bidders) | **최근 7일** 후 삭제(요약 생성 뒤) | ~170MB |
| 공고(notices, 첨부 포함) | 최근 60일 | ~125MB |
| 계약(contracts) | 최근 30일 | ~150MB |
| companies·agencies·stats·사용자 데이터 | 영구 | ~40MB |

과거 공고 검색은 이미 있는 **나라장터 실시간 모드**(12개월)가 담당 — DB 창 밖 검색 시 안내는 005에서 구현됨. 유료 전환하면 보존 창만 늘리면 된다(정책이 코드에 상수로).

## 의존 관계 요약

```
009 안정화 ──► 018 조직 ──► 019 초대 (협업 트랙, 최우선)
   │              └────────► 014 경쟁사 프로파일
   └──► 010 모니터링 ──► 011 numeric 결정 ──► 012 예산·prune + 낙찰 3개월 헤더·요약 백필
                                                └──► 015 통계 ──► 016 추천 구간
013 사전규격 추적: 독립, 아무 때나 병렬
017 낙찰 실시간: 활용승인 대기
```
핵심 차단선: **011(numeric)은 반드시 012 전에** / 010 없이 장시간 백필 런을 돌리면 실패를 늦게 안다 / 015는 012의 요약·헤더 축적 전제 / **012의 prune이 돌기 전까지는 일일 수집이 무료 한도를 갉아먹는다(약 2주 여유) — 009·018보다 먼저 최소 prune만 당겨 넣을지는 009 계획 시 판단**.

## 검증 방법 (런 공통 + 트랙별)

- 각 런: plan-and-build A블록(typecheck·test·build·lint 0·generate 무변경) + 검수자 B블록(실 DB·실 API).
- 018: 기존 사용자 데이터가 개인 org로 무손실 이관(행 수 전후 일치), 교차 조직 404 회귀 테스트, `/api/me/*` 15개 라우트 무변경 통과.
- 019: 초대 메일 실발송 1회(Resend) → 수락 → 멤버 목록 반영; 미로그인 수락 시 로그인 후 복귀.
- 010: webhook.site로 관리자 웹훅 3경로(알림 실패·백필 정체·Actions failure) 실수신.
- 012: prune 후 DB 총량이 예산표 이내(`pg_database_size`), 요약이 삭제 전 반드시 생성됨(요약 없는 행 삭제 0 테스트), summary-only 백필 3개월 후 awards 행 수=API 공고 수, 1일치 백필 소요시간 전후 비교.
- 015/016: 셀 1개를 원시 SQL로 직접 집계해 `award_stats`와 일치, n<30 폴백 경로 테스트.

## 백로그 (런 진행 중 발견)

- **B20 `MAX_PAGES.award=150` 상한 초과** (2026-08-31 백필 실측): 6월 공사(Cnstwk) 하루가 150페이지(149,850행)를 초과해 summary-only 백필이 "페이지 상한 도달" 오류로 실패(6/09·16·17·18 실측). 012 재검수가 경고한 "여유 8%" 경로가 실제 발생. 임시 조치: 백필 워크트리에서 award 상한 400으로 패치해 재처리. 근본 수정: `packages/nara-api/src/opnstd.ts:13`의 award 상한 상향(또는 CLI 플래그화)을 다음 안정화 런에 포함.
- **B21 검색 통계 첨부 무음 catch** (016 검수 MINOR): `apps/web/src/server/search.ts:279-285` — 통계 첨부 실패가 로깅 없이 삼켜져 조회 실패와 표본 부족이 구분 불가. 로깅 한 줄 추가.
- **B22 summary-only 실패 잡 재선점 주의** (012 재검수 MINOR): failed로 남은 백필 잡을 야간 run-once가 full 모드로 재선점 가능(사전 존재 사항) — 보존 창 밖 날짜면 bidders에 대량 상세행이 들어올 수 있음. prune이 다음 주기에 정리하므로 치명적이지 않으나 문서화 필요.
